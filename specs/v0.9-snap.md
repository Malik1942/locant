# Locant v0.9: Snap and Cut take the element

**Status:** Spec written Sep 29, 2026, after Malik found that Snap could not capture a hover state and that Option did nothing in it. Decided the same day: option A, the ladder everywhere and ⌘ for clipboard-only. Ships with `specs/v0.9.md` as 0.9.0.
**Scope of this spec:** Snap and Cut hover the element under the cursor the way Point and Text do, Option steps up the ladder, the window is the ladder's top rung, and "keep it off disk" moves from ⌥ to ⌘ on the overlay and on the ring. The one-shot pixel order (R76 in `specs/v0.9.md`) is the other half of the same finding.
**Out of scope:** a sidecar or a note for Snap; padding around a snapped element (the outline is what gets snapped); a frozen frame (v0.1 R2 chose the live overlay, and that stands); changing Point's readout for real window elements.

Read `CLAUDE.md`, `specs/v0.3-actions.md` (R22, R23, R26, R27), and `specs/v0.9.md`.

## 1. What is wrong today

| Action | Hover | Click | ⌥ |
|---|---|---|---|
| Point | the element, Option walks up | the outline | up a level |
| Text | the element | the outline, +8 pt | up a level (already; the code path is Point's) |
| Snap | the window | the window | held at the click: clipboard only |
| Cut | the window | the window | held at the click: clipboard only |

Four actions on one gesture, two meanings for the outline and two for ⌥. A lit button cannot be snapped by itself; only by drawing a frame around it.

## 2. Requirements

**R77. The ladder in Snap and Cut.** Snap and Cut leave the window-only hover and take Point's: the accessibility read at the cursor, `HitRefiner.selectionLevels`, the stickiness across padding, Option to step. Their ladder ends in the window: `HitRefiner.addingWindow(levels, window:appName:)`, pure, drops the empty rungs and appends a `window` element (role `window`, label the app's name, frame the window's bounds) unless the top rung already spans it. Where there is no element at all (Figma, a canvas) the ladder is the window alone, which is today's behavior. Where there is no normal window either (the desktop, the menu bar, the Dock) the ladder is the elements alone. The readout for the window rung reads `window · Safari`, as it did before. Click and Return take the outline at its level, exactly; a drawn frame is unchanged.

**R78. ⌘ keeps it off disk.** On the overlay, ⌘ held at the click or Return means clipboard only for Snap and Cut; ⌥ is the ladder's, everywhere. On the ring, ⌘ held at release means the same, and the small badge beside Snap and Cut reads ⌘. Toasts are unchanged (`Snapped · 640×480 · clipboard only`).

**R79. Copy.** The hint line for Snap and Cut: `↩ picks · drag for a frame · ⌥ up a level · ⌘ clipboard only`; for Text: `↩ takes the text · drag for a frame · ⌥ up a level`. The help page's Snap and Cut rows say element, window, or frame, and ⌘. README: the two action lines, the limitation that said Snap and Cut take a window only, and a CHANGELOG line. The site says nothing about ⌥ on Snap, so nothing changes there.

## 3. Tests

- `SnapLadderTests`: the window is appended after the elements; an empty ladder becomes the window alone; a top rung that already spans the window is not doubled; a nil window leaves the elements alone; nil rungs are dropped.
- The existing tests pass.
- By hand: hover a toolbar button in Snap and see it outlined; ⌥ once outlines the toolbar, ⌥ up to the window; click snaps the outline exactly; ⌘-click leaves nothing in `~/Pictures/Locant`; in a blank area of a window the outline is the window; over Figma's canvas the outline is the window; on the ring, ⌘ shows the badge and the release keeps it off disk.
